### PR 408 — VA-API hardware decoding + H.264/H.265 export encoding

- Builds clean, `cargo clippy --all-targets -D warnings` clean.
- **Bug (test robustness, not a GPU-dependent bug):** `crates/platform/tests/vaapi_export.rs:116` (`what_the_gpu_does_not_take_goes_to_the_software_encoder`) assumes a real VA-API hardware encoder is present and has no skip-if-absent guard, unlike its sibling test `hardware_export_matches_the_software_export` (same file, line ~94), which checks `if after.sessions == before.sessions { eprintln!("SKIPPED..."); return; }` before asserting anything. This sandbox has no `/dev/dri` (no GPU), so `filmcraft_platform::register()` never registers the VA-API encoder factory at all (`crates/platform/src/lib.rs:85-87` returns `Unavailable` early), and every assertion that expects a specific decline/frame count fails outright: confirmed `assertion left == right failed: left: (0, 0) right: (0, 2)` at `crates/platform/tests/vaapi_export.rs:129`. This will fail identically on any CI runner without a GPU/DRI device (which is most hosted CI). Fix: add the same skip-if-no-hardware guard used by the sibling test before the per-case assertions.
- Conflicts with `upstream/main` on 19 files (Cargo.lock, both app `main.rs`, `crates/codecs/src/hw_frame.rs`, `crates/h264/src/decoder.rs`, `crates/hevc/src/decoder.rs`, all of `crates/platform/src/vaapi/*` as add/add conflicts, `crates/platform/src/lib.rs`, docs). Needs a rebase.
- Heavily overlaps PR 409 (see below) — both branches independently add the same `crates/platform/src/vaapi/{ffi,mod,h264,hevc}.rs` files, so they will also conflict with each other if both are rebased. WISHLIST.md already flags this ("Both conflict with main").
