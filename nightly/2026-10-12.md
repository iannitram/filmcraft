### Findings (cloud CPU, single decode thread)
- Profile of the full decode (`perf` works after `apt install linux-tools-6.8.0-31-generic` and `sysctl kernel.perf_event_paranoid=-1`): `slicedec::predict_block` (motion compensation) 20%, `deblock::deblock_mb` 14–16%, CABAC residual decode 12%, CABAC macroblock decode 5–6%, `inter::weighted_store` 3.5%, and kernel time (page faults, `clear_page`, thread wake-ups) about 8–10%.
- Turning parts of the deblocking filter off in a throwaway build shows what it costs: the edge filtering is about **18%** of decode time, and the bS (filter strength) decisions about **6%**.
- `crates/h264/src/deblock.rs` `filter_vertical`: in the crate's own micro-benchmark, a vertical edge costs about 3.5x a horizontal edge (~100 vs ~29 ns). The difference is rearranging bytes into "one lane per line". But that micro-benchmark only runs for ~2 ms and swings 2x between runs (101 vs 220 ns for the same code), so it can't judge a change.
- The page-fault / `clear_page` time comes from the `h264dec` example using no plane pool (`picture.rs` `plane_allocator` falls back to `Vec::with_capacity`). The app installs a pool (docs/performance.md MEM4), so this cost doesn't show up in real editing. It isn't a target.
